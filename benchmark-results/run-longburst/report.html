Batch vs Live Traffic Isolation

Workload

This benchmark tests whether the llm-d-async dispatch budget gate protects live inference traffic from batch request interference. Two scenarios are compared on identical hardware:

ModelQwen/Qwen3-8B on 1x NVIDIA A100 GPU
Live trafficguidellm burst/idle cycles: 15 req/s for 300s (burst), 1 req/s for 120s (idle), 2 cycles
Batch load10000 requests submitted at start (idle), another 10000 submitted during first burst
Batch requests~2000 random input tokens, no output cap (defeats prefix caching)
PatternIDLE → BURST → IDLE → BURST

Sync (no gate)

Batch-gateway processor sends requests directly to the inference gateway. Batch and live traffic compete for GPU capacity.

Gated (async dispatch)

Batch-gateway submits to a Redis queue. The async-processor dispatches only when the prometheus-budget gate is open (GPU utilization below threshold).

Each burst phase sends requests at 15 req/s for 300s. Requests still in-flight when the phase window closes are marked incomplete — they were delayed by GPU contention from concurrent batch processing. Every batch request dispatched during burst is capacity stolen from live traffic.

Conclusion

Without the dispatch budget gate (sync), the batch processor sends 10000 requests directly to the inference gateway during burst, competing with 15 req/s of live traffic for GPU compute. During burst phases, 2925 of 3436 live requests completed in time (TTFT 246.4 ms), while 26 batch requests consumed GPU capacity that could have served live traffic.

With the prometheus-budget gate, the async-processor monitors GPU utilization via Prometheus and holds back batch requests when the inference endpoint is saturated. During burst, only 12 batch requests were dispatched, allowing 3056 of 3567 live requests to complete (TTFT 239.1 ms). Batch work shifts to idle periods (51 requests processed during idle) when GPU capacity is available.
